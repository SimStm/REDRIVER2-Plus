## Tool source attribution and limits

The [Vulkan access-stage table](https://docs.vulkan.org/spec/latest/chapters/synchronization.html#synchronization-access-types-supported)
requires HOST for HOST_READ; the recorded validation error is real for the
reported masks. Context7 was consulted, then the current primary specification
was checked because a legacy example combines host accesses with ALL_COMMANDS.

Official RenderDoc [v1.41 queue capture source](https://github.com/baldurk/renderdoc/blob/v1.41/renderdoc/driver/vulkan/wrappers/vk_queue_funcs.cpp#L1227)
performs GPU readback of mapped memory for capture comparison. Its internal
readback barrier requests HOST_READ and calls `DoPipelineBarrier`.
The [v1.41 helper](https://github.com/baldurk/renderdoc/blob/v1.41/renderdoc/driver/vulkan/vk_common.cpp#L683)
uses ALL_COMMANDS for both stages. These internal unwrapped commands bypass the
application-command serialization, while the queue wrapper serializes collected
debug messages. This provides source-backed attribution to capture instrumentation,
consistent with the stored warnings and absent application buffer barriers.

The exact injected-binary call stack was not collected. This does not establish
that every Vulkan warning is owned by RenderDoc, prove every game frame clean,
repair RenderDoc or authorize filtering/clearing its messages. Do not change the
configured1.41 version or application barriers as a workaround. A tooling fix
would need its own instrumented capture/control evidence.
